# 常见故障与恢复

## 无法发起支付，请重试

按此顺序读证据，避免盲目重试：

1. 确认当前用户、SKU、渠道、环境、部署版本；查看浏览器请求结果和服务端脱敏错误，不打印凭据或带 token 的收银台链接。
2. 检查正式店铺权限、生产商品状态/币种、商品映射与密钥环境，开发者页可能另有测试/正式开关。
3. 核实后台配置确实保存，生产秘密已进入当前运行部署，配置缓存已更新。
4. 查询本地未付款订单/支付预留、平台已有会话/订单及外部引用。此前自动验收可能已经留下一个可付款会话，再点购买被防重复逻辑拦截。
5. 若原收银台仍有效，优先在原标签页恢复并向用户说明。会话 token 失效和订单到期不是同一个概念，按当前官方机制恢复，不盲目复制旧链接。
6. 不支持安全恢复时展示“已有待处理订单”和明确下一步，而不是仅泛化“请重试”。本地 manual_review 不是平台取消。
7. 平台查询为空，可能尚未生成订单；本地等了 40 分钟等阈值，也不证明平台会话过期。读取实际 expiresAt/官方 TTL，不能据此删预留、解锁并创建另一笔可支付订单。
8. 不发明取消会话 API。某 SDK 的客户侧取消订单可能需要实际订单 ID 和客户会话，不能拿本地引用或 merchant 凭据代替。

## 付款成功但未到账

对齐平台订单、外部引用、storeId、环境、buyerIdentity 和当前登录用户。检查原始验签、事件收据、事务、账本唯一键、队列/重试及周期归属。用当前可信平台状态进行幂等对账，不能手工直接加余额再让迟到通知重复发放。成功回跳和用户截图是线索，不是后端发货凭证。

## 重复到账/订阅状态回退

检查业务幂等键和唯一约束、事务是否真实原子、多个 Webhook 重复投递、首期与激活事件重复授予、旧通知是否覆盖新状态。针对重现情况测试并修复；清理重复端点前确认别的生产消费者不依赖它。

## 退款后状态或积分没变

先确认退款是申请中、失败还是成功，以及是否退到了正确生产订单。检查退款通知订阅/验签/重试、原始授予关联和已消费权益政策。部分退款不自动等同于全部取消；退款成功也不自动等同于停止续费。

## 收银台国家不正确

IP/网络可能影响默认国家。实际账单国家由付款用户确认，不按当前时区、语言或商户结算账户猜填。核对最终税费与付款方式规则，不能承诺换国家一定出现特定渠道。

## 表单显示成功但刷新丢失

重新读服务端值，查保存接口、权限、字段名称、错误处理和缓存。仅点击成功不算持久化成功。修复根因后重新保存和读回；生产数据库写入必须满足共用配置流程中的条件。

## 升级和回滚

保留上次可用的非敏感配置映射、正式部署版本和事件覆盖记录。回滚代码不能回滚实际已收/已退款交易；通过幂等对账恢复业务状态。密钥泄露应按平台正式轮换流程处理，不能仅删日志就声称风险解除。
