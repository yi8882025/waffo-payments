# 共用：商品、密钥、通知与网站后台

## 1. 检查现有工程

找出当前支付适配器、后台设置、商品清单、下单接口、支付通知、订单表、权益账本、订阅管理和部署流程。优先融入现有架构。检查数据库是否真正支持事务/唯一约束，不把某项目封装的缺陷误认为数据库平台本身不支持事务。

建立环境映射：环境 → 商户 → 店铺 → 商品 SKU/平台商品 ID → Webhook → 密钥来源 → 部署 → 数据库。测试和正式分别登记；生产页面左侧选择了正式环境，也仍须检查开发者密钥页、商品页的独立环境开关。

## 2. 商品配置

用真实批准的目录清单填写名称、说明、类型、金额、币种、周期、税务类别及权益。价格用十进制字符串或最小币种单位，禁止浮点计算。不得默认所有币种都有两位小数。

- 一次性商品：明确购买后积分/权益数和有效期。
- 订阅商品：明确周期、每期权益、到账时点、结转规则、到期方式、是否有用户批准的试用。
- 周期以支付平台实际付费周期为准，不用固定 30 天替代自然月。
- 优惠、税和动态报价使用当前 SDK 支持的结构，并核对最终应付金额；不能只信前端展示价。

创建前列出现有商品，按稳定本站 SKU（可用 metadata）匹配，已存在就核对/更新。未知创建结果先查询；使用包含站点、环境、SKU、操作版本的稳定幂等键，不为重试生成新随机键。保存并重新读取类型、状态、币种、价格及商品归属。测试商品复制/发布到正式后，重新读取正式 ID，不直接复用测试 ID。

## 3. 密钥与 Webhook

在正确环境创建或复用有适当权限的服务端密钥，记录名称/指纹和所属环境，不记录私钥。密钥可能是 PEM 或原始 base64，使用官方 SDK 支持的规范化方式，并在内存中验证可解析性。检查可再次下载/托管选项的实际状态，不声称默认关闭。不要未经授权轮换或撤销在用密钥。

生产私钥放部署平台的服务端 Secret；测试密钥只放对应测试环境。不得放 `NEXT_PUBLIC_*`、浏览器配置或普通后台配置表。生产 Secret 更改后按部署平台要求重启或重部署，再核对运行版本和配置就绪状态。

Webhook 使用本站 HTTPS 路由。添加前列出现有 storeWebhook，按店铺、环境、URL 去重；避免重复端点造成多次投递。只订阅实现了处理器的事件，以当前 SDK 枚举核实名称。参考事件类别：一次性支付完成；订阅激活、支付成功、续费、恢复、变更、待取消、取消、逾期；退款成功/失败。配置后重新查询 URL、环境、启用状态及事件覆盖。

通知服务端必须：

- 使用原始请求体和当前官方签名算法/公钥验签，明确测试/正式环境；先验签再信任载荷。
- 验证预期 storeId、环境、订单归属、商品、币种和金额；商户身份按签名及官方资源查询核实。
- 将支付/退款业务更新与事件收据、权益变更放在真实原子事务内，使用唯一约束防止并发重复到账。
- 区分事件投递 ID、事件类型和业务实体 ID。同一个业务实体会有不同事件；不要只按实体 ID 去重所有通知。
- 按当前事件语义制定幂等键，通常至少含环境、店铺、eventType 和 eventId。响应成功必须表示已持久化，或已可靠入队且具备重试机制。
- 处理乱序/重复通知、退款早于付款处理、延迟成功及订阅旧事件；终态不能被更旧事件复活。

## 4. 下单与权益

用户身份、本站 SKU、价格、权限由服务端核定。推荐用稳定应用 userId 作为 buyerIdentity；buyerEmail 只预填邮箱，不能让客户改收银台邮箱就改订单归属。匿名结账只有在业务明确支持匿名订单认领时使用。

先记录本地订单与稳定外部引用，再以幂等方式创建结账。核实 SDK/API 的实际参数，不猜 cancelUrl/returnUrl 等字段。成功返回页不能单独发放权益；以验签通知或服务端平台核验为准。跳转后页面从后台读取到账状态，可轮询/刷新，不把“返回网站”当付款证据。

同一订单重试应恢复原结账或显示明确状态。不能因网络超时、查询为空或本地超时阈值就认定平台订单已取消。服务端并发锁、唯一约束与平台幂等一起防重复扣款。必要的对账任务要能补齐漏通知；用户要求定期监控时再建立自动任务。

订阅首期、续期、恢复与方案变更分别定义权益处理，按真实账期幂等入账。取消续费与退款独立处理；取消后付费期内访问按本站规则保留，不能一概立即清空。

## 5. 后台保存与部署

填写当前工程实际字段：启用开关、环境、商户/店铺标识、平台商品映射、Webhook、默认渠道、渠道选择及订阅/退款入口。字段名取自工程，不假设所有项目与示例相同。

保存后刷新后台并读取服务端配置，只显示密钥是否就绪。页面工具成功但不持久化时先修复保存接口/权限/缓存。仅在已授权且清楚数据库结构、回滚方式时使用窄范围事务写入，绝不把直接改生产数据库当默认步骤。配置缓存只针对相关标签失效。

部署前完成必要测试，确认当前生产版本及待部署差异。仅改秘密配置时复用确认的生产版本；不能把较旧的本地 HEAD 或其他任务的 UI 修改一起上线。部署后检查正式域名指向、配置就绪、下单接口、Webhook 响应和后台读取。
