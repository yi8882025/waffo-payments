# 验收、退款与对账

## 先测试环境，再正式环境

使用测试专用用户和隔离的数据，不通过生产余额伪造测试。记录平台真实订单号与本站订单引用，打码邮箱；测试证据不能代替生产证据。

| 场景 | 必须验证的结果 |
| --- | --- |
| 一次性付款成功 | 平台成功、本站已付、金额/币种/归属匹配、权益只到账一次 |
| 付款失败/放弃 | 不授予权益，能安全重试/恢复，状态说明清楚 |
| 连点/并发/网络超时重试 | 不重复创建可支付订单，不重复扣款/发积分 |
| 重复通知/并发投递 | 已持久化、幂等返回，账本只变更一次 |
| 通知伪造/错误店铺/错误环境 | 拒绝且不改订单或余额 |
| 回跳/刷新/关闭收银台 | 付款状态来自后端，不凭 URL 参数发货 |
| 延迟通知/漏通知 | 可对账补齐，晚到的成功付款不被本地超时丢弃 |
| 订阅首期/续费/失败恢复 | 每个真实账期到账一次，逾期与恢复一致 |
| 取消续费/撤销取消 | 平台与本站一致，付费期权益符合已公布规则 |
| 全额/部分退款/失败退款 | 金额、状态、订单、权益账本一致且不重复回收 |
| 通知与客服 | 用户能找到收据、订阅管理、取消/退款入口，通知到正确收件人 |

只测试当前商品支持的场景；不支持部分退款、订阅等的条目标为“不适用”并写依据，不能伪造通过。针对并发、幂等、乱序、错误环境和权益变更写有意义的测试，不只测试函数是否被调用。

正式冒烟测试：取得真实小额付款所需授权，使用用户批准的商品和专用账号，用户自己输入付款资料并支付。不要为“验证能打开收银台”给主账号留下未完成正式订单。记录未付款会话的真实到期时间和安全恢复方式；没有取消 API 就不要假装已清理。支付后分别核对平台订单、本站订单、实际到账权益、收据和回跳体验。用户报告已支付但无法独立核对时明确标记“用户反馈成功”。

## 退款执行

1. 读取当前退款能力、账户合同/费用和后台状态；不同付款方式可能只支持全额或不支持退款。不写死手续费或到账天数。
2. 根据用户提供的具体订单定位：环境、店铺、平台订单号、本站订单号、付款时间、付款人、已付金额/币种、已退金额、可退余额及权益消费情况。不要按同金额猜订单。
3. 核实用户授权范围：明确订单和全额/部分退款额度。没有操作授权就停在准备好的退款摘要/界面，必要时仅询问缺少的信息；不因用户要求“写退款流程”而发起真实退款。
4. 在官方后台订单详情/当前官方 API 准备退款，核对金额、币种、原因及影响。使用平台支持的幂等机制；结果未知先查退款列表，不重复提交。
5. 提交后记录退款 ID/状态、平台提示和时间；请求受理不等于退款成功。等待事件或查询确认，再与本站同步。
6. 权益处理按本站已批准政策：未使用的全额退款可原子回收对应原始授予；部分退款或已消费权益按明确规则处理，没有规则就转人工，不擅自按比例扣分、不任意扣到负数。退款重复通知不能重复回收。
7. 区分“退款请求已提交”“平台退款成功”“客户账户已入账”。最后一项需要买家/银行证据，不能承诺即时到账。
8. 订阅取消与退款分别核对；退款不必然停止续费，取消续费不必然退已收款。若用户要求两者，分别执行并验证。

## 验收记录模板

在项目支付记录中使用以下结构，只有非敏感资料：

```text
站点/日期/执行范围：
商户/店铺/环境：
批准的商品清单及测试/正式 ID 映射：
后台与部署版本：
密钥来源与就绪状态（不含密钥）：
Webhook 路由、事件覆盖、去重状态：
结算账户掩码及验证状态：
默认渠道/备选渠道及用户选择依据：
场景 | 环境 | 实际证据 | 结果（已验证/用户反馈/待验证/不适用）
退款对象/额度/平台状态/本站权益状态：
未付款订单及恢复方式/真实到期时间：
待处理问题、下一步及回滚方法：
```

交付只陈述实际证据。不得把后台已填、正式页面可打开、测试付款通过或用户看到退款按钮分别替代“正式收款与退款全流程完成”。
